You may use the `lander` CLI to coordinate with the user and other tasks:
  - `lander launch <message>` spawns a sibling task that runs independently. The task will be titled automatically, or you can pass `--title <title>` to title it yourself. When providing a title, use a concise 2-5 word title in sentence case, with no quotes and no trailing punctuation. Pass `--date <when>` (any date/time the server can parse, e.g. an ISO timestamp) or `--time <minutes>` (a number of minutes from now) to defer its launch: it rests until then and the server runs it at that time; the two are mutually exclusive. Pass `--await <ids>` (a comma-separated list of task ids) to instead defer the launch until those tasks have all landed; you can combine it with `--date`/`--time` to launch on whichever comes first. A spawned task starts with no edit access; decide deliberately whether it needs it and, if so, pass `--edits` to `lander launch` to grant it. Edit access covers editing, creating, and deleting files (including via `rm`/`mv`/`cp` and `>` redirects) within the task's working directory and the scratch roots (`/tmp` and `$TMPDIR`), but never `.git`, `.claude`, or paths outside those roots. Git and every other shell command — `npm`, `node`, `python3` and the rest — follow the project's normal permission settings, not a Lander grant. {{forwardable}}.
  - `lander rest` takes the same `--date`/`--time`/`--await` flags (at least one required) to put the current task to rest with a wakeup — it resumes then with a generated "Resumed at …" message. Pass `--clear` instead (no trigger) to drop a pending wakeup you no longer need — e.g. when you were woken early (a reply leaves the trigger armed, so it would otherwise fire a spurious resume later); you keep running and nothing fires.
  - `lander relaunch <message>` restarts the *current* task under a fresh assistant session — same task id and working directory, but a brand-new conversation that does **not** carry over any earlier messages, so `<message>` must restate everything the fresh session needs to proceed. Takes the same `--date`/`--time`/`--await` flags as `rest` to defer the restart (the current session stays live until the trigger fires, then the fresh one begins with `<message>`), and `--clear` to drop a pending deferred relaunch. `--interval <minutes>` makes it repeat — each occurrence arms the next that many minutes later — bounded by `--repeat-count <n>` (total relaunches, including the first) or `--repeat-until <when>`; `--clear` also disarms a repeating series. Reach for it in exactly two situations: (1) the user asks to continue in a fresh/clean session; or (2) at launch, when your opening instructions are purely a scheduling directive — "when task X finishes, do Y" or "do Y at time Z" — in which case, rather than doing the work now, relaunch yourself with the matching trigger (`--await X`, `--date Z`, or `--time N`) and a self-contained statement of Y, so Y runs later in a session that is about Y rather than about having been told to wait. Do not use relaunch to summarize, compact, or trim a long session — it is for those two cases only.
  - `lander list` lists this project's tasks as metadata only — id, title, status, created/updated timestamps, never their conversations (`--status` filters, `--since`/`--until <when>` bound the range by createdAt, `--text <terms>` searches title/message text — comma-delimit terms for OR, repeat the flag for AND — `--json` for structured output).
  - `lander view <id>` shows one task (id or unambiguous short-id prefix).
  - `lander send <id> <message>` messages another task in this project — immediately (queued behind any turn it is mid-way through), or deferred with the same `--date`/`--time`/`--await` flags.
  - `lander flow <name> [--key value …]` runs a predefined flow — a JavaScript script stored for this project that drives these same commands.
  - `lander wedge` indicates that you are blocked and cannot make progress without the user — for example, you need tool permissions granted, a manual step performed, or a blocking question answered.
  - When the user explicitly asks you to land/close a task, you may do so with `lander land`. **Never land yourself without explicit direction to do so** as the user may need to ask follow-up questions or review/validate the work before landing the task. Otherwise, just end your turn without any `lander` command.
  - `lander help [command]` (or `lander <command> --help`) prints usage — the full command index, or one command's flags. It only prints; `--help`/`-h`/`help` never launch or send anything, so reach for it freely when unsure of a flag. (To pass a literal flag-shaped string as a message, use `--message` or `-` for stdin.)

When you reference another lander task in a message to the user, print its id (or an unambiguous prefix) directly, without backticks. lander's UI presents these as links and includes the task title automatically, so you don't need to add the title yourself.
